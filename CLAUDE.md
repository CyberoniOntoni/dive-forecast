@AGENTS.md

## What this is

`dive-current`: a Next.js 16 / React 19 app that forecasts current (direction, strength, confidence) at Maldives dive sites, hour by hour for about a week. No database on Node: all state is JSON files under `data/`; on Cloudflare Workers the mutable store is in D1 (see Deployment). How the model works today is in `FORECAST_MODEL.md`; the reasoning, calibration runs and findings log are in `HYDRODYNAMICS_PLAN.md`; product scope is in `ROADMAP.md`.

## Commands

```bash
npm run dev                  # http://localhost:3000
npm test                     # vitest run (lib/**, components/**, tests/**)
npx vitest run lib/forecast.test.ts          # one file
npx vitest run lib/forecast.test.ts -t "name" # one test
npm run lint
npm run build
npm run replay               # benchmark replay of past reports; writes data/replay.json
npm run cf:build             # Cloudflare Workers build (OpenNext); cf:preview builds and runs it locally on :8787
```

CI (`.github/workflows/ci.yml`, Node 22) runs `npm test`, `npm run lint`, `npm run build`, `npm run replay` — run all four before pushing.

Data/maintenance scripts (all `tsx scripts/*.ts`): `audit-sites` (flags catalog pins that disagree with the outlines, islands or each other; changes nothing), `atoll-openings [-- --from-tiles --ways <way-id,…>]` (reef gaps into `data/openings.json`; `--from-tiles` reads the map's Atlas tiles instead of the Atlas download and replaces only those outlines' rows), `verify` (score saved predictions vs. diver reports, grouped by model version), `benchmark`, `bearings -- <site-id>`, `site-types [-- --write]`, `channel-widths` (candidate Atlas channel widths, printed for review), `channel-depths` (channel depths on the Rasheed 2021 grid, printed for review; grid in `data/sources/rasheed-2021/`), `atlas-overlays [-- reefZones|bottomTypes|reefOutline]`, `wave-exposure [-- <site-id>…]` (each site's share of offshore swell and wind waves by direction, printed for review), `islands -- <land_polygons.shp>` (writes `data/islands.json` from OSM land polygons), `shoals` (writes `data/shoals.json`, lagoon reef tops and sand shallows from the Atlas reef-zone tiles in `public/overlays/reef-zones`), `shelter-grid` (writes `data/shelter-grid.json` for the sheltered-water map layer, one process per core; rerun after rims, openings, islands or shoals change), `extract-dive-guide`, `import-dive-guide`, `tide-check` (times the model's tide slope against the UHSLC gauges at Hanimaadhoo, Malé and Gan; best lag should be 0; exits 1 otherwise; needs network), `d1:export [-- <file>]` (writes the live worker store from D1 as `data/store.json` or the given file; needs wrangler signed in).

Calibration scripts (print tables; they set no constants themselves): `throughflow-calibrate` (K), `along-reef-calibrate` (walls), `atoll-head-calibrate` (τ; point `MARINE_CACHE_DIR` at a fresh dir so all series share one model run), `strength-calibrate` (channel and wall bands) and `lagoon-calibrate` (lagoon). The last two fetch 99-day series into an OS-temp cache via `scripts/long-series.ts`, never into `data/marine-cache`. See `FORECAST_MODEL.md` § Constants.

Tests run with networking disabled and a throwaway `MARINE_CACHE_DIR` (see `vitest.setup.ts`); any test needing Open-Meteo data must stub `fetch` or write fixture hours itself.

## Architecture

Data flow: `marine.ts` → `load-site.ts` → `forecast.ts` → pages/server actions.

- **`lib/marine.ts`** fetches Open-Meteo sea level + ocean current (1 past + 7 forecast days) for a point ~3 km *seaward* of each pin (opposite the inward bearing), with a file cache in `data/marine-cache/` (on Cloudflare the R2 bucket `CACHE` in Asia-Pacific, looking in `DATA` for keys it lacks until 12 Nov 2026, `lib/cache-bucket.ts`; with a per-data-centre Cache API copy kept 24 h, `lib/edge-cache.ts`; 6 h TTL refreshed in the background; an edge or memory copy past the TTL is checked against R2 before it is used, Open-Meteo only behind the response; on Cloudflare an hourly cron at :50, `lib/warm.ts`, refreshes every series at 4.5 h and builds the next hour's map nowcasts, CLOUDFLARE.md § Cache warm-up; a series fetched over 12 h ago (by age alone), whose newest hour is over 12 h old, or the last cached one after failures is marked `stale`, max 4 concurrent requests, per request on Cloudflare; the map passes `{ wait: false }` so it never waits on a first fetch). `{ past: true }` fetches the long past window instead (`REPORT_PAST_DAYS` = 16 past days, 2 ahead, cached under `past_`), only for a report whose dive the week's series no longer holds (`reportTideAnyAge` in `lib/actions.ts`); its prediction is then saved as a `hindcast`.
- **`lib/bearing.ts` / `lib/rim.ts`** resolve a site's inward bearing: explicit `inwardBearingDeg` override → rim-derived normal from the atoll outline in `data/rims.json` (pin within 0.8 km of rim) → fallback heuristic. The bearing drives the arrow, the drift projection, and where marine data is sampled, so a wrong bearing fails silently. Follow `ADDING_SITES.md` when adding or editing sites.
- **The site type picks the model** (`lib/site-type.ts`; details in `FORECAST_MODEL.md`):
  - **Across the rim** (passes, channel thilas, corners, walls within 0.8 km of a pass): `forecastHours` in **`lib/forecast.ts`**. Net flow = residual tide slope (25 h mean removed) + through-flow (`K` × 25 h drift along the inward bearing; the drift is averaged with nearby catalog across-rim sites' sample points, `lib/drift-smoothing.ts`, because the ocean model's 8 km cells can split neighbours) + head across the atoll (site level − atoll ring level, over `τ`). Direction is its sign; strength ramps hour by hour up to an envelope from the effective range (tide range + extra from through-flow/head, × channel constriction) in `RANGE_BANDS_M`. Reports (90-day half-life) fit a phase lag and speed factor and pull the next 6 h; confidence has hard gates (never "high" if a recent report contradicts, at walls or lagoon sites, or while the replay fails).
  - **Along the reef** (other outer-reef walls, or any with `alongReef: true`, `flowsAlongReef`): `alongReefHours` — the current projected on the reef line, tidal part ×3 (less where the cell's own tidal stream is already strong, `alongTideGain`) plus drift; shown as a compass direction.
  - **Lagoon**: `lib/lagoon-flow.ts` — 2-D sources at the rim's openings (ring points, weighted by the share of their stretch not backed by an island, `lib/rim-land.ts`, and channel sites, each with its channel-model net flow) plus a sink over the lagoon area; projected on the site's main flow axis (or the owner's `flowAxisDeg`) and shown as a compass direction.
  - A site with `flowFromSiteId` shows that catalog channel's forecast (`followTarget` in `lib/site-type.ts`, `flowSite` in `lib/load-site.ts`; a pin on a channel's wall that the outline puts in the lagoon): its place, bearing, section and curved outgoing heading (`SiteLoad.outgoingBearingDeg`), with reports at either pin teaching both (`forecastReportsForFlow`). It never crosses the rim, adds a funnel or opens a boat-route gap itself.
  - Along-reef and lagoon sites set `SiteLoad.alongHeadingDeg` ("incoming" = toward it); the UI, report form and `alongReportDirection` key off that.
- **`lib/atoll-ring.ts`** loads 12 ring points round each atoll outline (cached like any sample point, memoised 10 min per atoll); their mean residual level is the lagoon level for the head term (at an hour with points missing, predicted from the others by least squares over the hours with all of them, so it does not step; the plain mean of those present when fewer than 48 such hours), and their series are the lagoon model's rim openings.
- **`FORECAST_MODEL_VERSION`** in `forecast.ts` must be bumped whenever a change alters output for the same inputs — every saved report stores the prediction shown with that version (`lib/forecast-log.ts`), and `npm run verify` groups by it. Past predictions are never recomputed.
- **`lib/load-site.ts`** assembles a `SiteLoad` for a site (routing by model above; per-atoll memo of lagoon openings); it reads `data/replay.json` and blocks "high" confidence while the replay says `ok: false`. `lib/nowcast.ts` does the same for all sites at the current hour (map glance, `lib/nowcast-glance.ts`).
- **Strength** is stored as `slack | mild | strong | too_strong`; `too_strong` is *shown* as "very strong" (it depends on the diver whether it can be dived).
- **`lib/store.ts`** reads the seeded catalog `data/sites.json` (read-only at runtime) and the mutable `data/store.json` (reports, ratings, user-added sites with `sourceUrl: "user"`), writing via temp-file + rename under a serialized mutation queue (process-local only). On Cloudflare the store is in D1 (`lib/store-d1.ts`: one table per list, rows as JSON; a request reuses its isolate's copy while the `store_version` row is unchanged; `mutateStore` writes only the rows a change touched, in one batch guarded against stale reads, and retries the change on a conflict, so `mutate` must be safe to run again); the old R2 `store.json` was copied in once and kept as a backup (delete it so account deletions reach it, `CLOUDFLARE.md`). `npm run d1:export` writes the live D1 store as a `store.json`. `lib/actions.ts`, for accounts `lib/account-actions.ts`, and for terms, reports, blocks and moderation `lib/moderation-actions.ts` (all `"use server"`) are the only entry points from the UI for reads/writes.
- **Accounts**: reporting, rating and adding sites need a signed-in diver (`requireSession` in `lib/auth.ts`); reading is public. Email code sign-in (`lib/account-actions.ts`, `lib/accounts.ts`; sent by Cloudflare Email Sending, the worker's `EMAIL` binding, with Mailgun as fallback and the only route on Node: `lib/email.ts`, `lib/mailgun.ts`), a stateless HMAC-signed cookie (`lib/session-token.ts`, `AUTH_SECRET`). Users (with an optional "About me" shown on their public page `/divers/<id>`) and hashed pending codes live in the store; only nicknames are ever shown, never emails. Points, badges and the public scoreboard (`/scoreboard`: reporters by points, plus divers who added sites) are computed from reports and site ratings on the fly (`lib/points.ts`, rules in `lib/points-rules.ts`); ratings are one per diver, averaged. A diver deletes their account on `/account` or in the app (`DELETE /api/v1/me`): `deleteAccountRecords` in `lib/accounts.ts` removes the user, codes, plans, ratings and their photos, and keeps reports under a fresh random `deleted-…` id (still one diver to the forecast); a session whose user is gone no longer counts (`lib/auth.ts`). Keep `/privacy` (`app/privacy/page.tsx`, linked from Google Play) true to what is collected. User content follows Google Play's UGC policy (`lib/moderation.ts`, `lib/moderation-actions.ts`): agreeing to `/terms` at sign-in (`acceptedTermsAt`; posting reviews, photos, sites or About me needs it), Report (`flags` list, D1 table `flags`) and Block (`User.blocked`, hides their reviews and site notes from the blocker) on the web and in the app, and `/moderation` for `MODERATOR_EMAILS` (remove, ban with `bannedAt`, dismiss; below the open reports, the last 30 days of activity from `lib/activity.ts`: dive reports, reviews and ratings, added sites, plans, sign-ups and content reports, store-review content labelled, with Remove / Ban straight from the feed via `moderateContent`, and Hide report / Hide all their reports via `moderateReports`: a hidden dive report keeps its row with `Report.hiddenAt` but is left out of `countedReports` and `visibleReportsForSite`, so it stops teaching the forecast and leaves verify, points and listings). A store-review account (`lib/review-account.ts`: `REVIEW_EMAIL` signs in with the fixed `REVIEW_CODE`, no email sent, never a moderator; signing in with the code sets `User.storeReview` for good, so its reports never teach the forecast (`countedReports` / `forecastReportsForSite` in `lib/store.ts`), earn points or count in verify, its reports and ratings are shown only to itself (`visibleReportsForSite`, `ratingsForSite`), it is off the scoreboard and has no public diver page, and deleting it deletes its reports and hides its sites) is for Play Console's sign-in details. Setup in `CLOUDFLARE.md` § Sign-in.
- **Site details from divers**: the add-site form (`components/AddSiteForm.tsx`) also takes the kind of site (`diverSiteType`), dive depths (`diveTopM`/`diveMaxM`), "how to dive it" notes, the adder's rating and up to 6 photos (`lib/site-details.ts`, `lib/site-photos.ts`). An app-added pin's `siteType` (so its model) comes from its position, or on the rim band from `diverSiteType` (`withCurrentPlace` in `lib/store.ts`; FORECAST_MODEL.md § Pins added in the app); depths and notes are display only. Photos are shrunk and re-encoded to JPEG in the browser (`lib/photo-shrink.ts`, 1600 px, ≤ 1.5 MB, so `serverActions.bodySizeLimit` is 2 MB), sent one per `addSitePhoto` call, stripped of EXIF on the server, and kept in R2 under `site-photos/` (`data/photos/` on Node); `/site-photos/<site>/<photo>.jpg` serves them. Only the adder adds photos, on the form or later on the site page (`components/SiteAbout.tsx`). On any site, catalog ones too, a signed-in diver's rating is also their review (`components/SiteReviews.tsx`): text and up to 6 photos on their `Rating` row, changeable or removable; a removed rating stays as a row with `removedAt` and `firstRatedAt`, and rating points count on `firstRatedAt`, so undo and re-rate earn nothing new. Reviews and photos earn no points; review photos are capped at 24 a day per diver from `User.reviewPhotoUploads`, so deleting does not give uploads back.
- **JSON API for the Android app** (`android/`: Kotlin/Compose, its own Gradle build outside the npm scripts, with its own `android` CI job; `android/README.md`): `app/api/v1/*` (GET `sites`, `sites/<id>`, `sites/<id>/forecast`, `nowcast`), shaped by `lib/api-v1.ts` over the same server actions, so the model is untouched; every hour carries a `glance` (arrow, words, tone) made by `lib/nowcast-glance.ts`, so the app keeps no copy of the display rules; response bodies are allow-lists; contract and versioning rules in `API.md`. The app stays in this repo on purpose (`android/README.md` § Why the app lives in this repo). Responses never carry a diver id or email. Adding a field is fine; a breaking change needs `/api/v2`.
- **Boat navigation**: the site page's "Navigate here by boat" opens `/?navigate=<id>`; `components/BoatNav.tsx` follows the phone's GPS (speed/course in `lib/boat-nav.ts`) and asks `getBoatRoute` for a route. `lib/boat-route-data.ts` loads the shapes (islands, shoals, outlines, `data/openings.json` gaps, pass sites) and `lib/boat-route.ts` runs A* on a ~50 m grid that blocks islands and shoals, crosses outlines only at those gaps (reef-flat sills last), and falls back to a straight line. Satellite outlines, not a chart. The route also carries the forecast current along it (`lib/route-current-data.ts`: a nearby site's forecast as its arrow heading at a typical speed per band, the Open-Meteo ocean current beyond the outlines, none inside a lagoon away from sites); `lib/route-current.ts` turns it into the steer bearing that holds the track and a time-stepped ETA. The forecast model is untouched.
- **Dive plans**: a signed-in diver (guide, liveaboard) makes a plan of days and dives (site + time, optional note and wanted direction at a channel) at `/plans/new`; `/plans/<id>` is the public share page (16-letter random id, noindex), editable only by its owner. Stored as `DivePlan` in the store's `plans` list (D1 table `plans`). `lib/dive-plan.ts` validates input and reads each dive against the site forecast (`stopOutlook`: warnings for very strong at or the hour after the dive, wrong way at a channel, rough sea; `bestWindow` suggests a warning-free daylight window), `lib/plan-view.ts` builds the page, `lib/plan-actions.ts` saves/deletes and plans each day's boat legs (`planLeg` in `lib/boat-route-data.ts`, no current) on request. After a dive, each stop links to the site's report form at the dive time (`/sites/<id>?at=…#report`). The forecast model is untouched.
- **UI**: `app/page.tsx` (map with nowcasts, `components/SiteMap.tsx` on Leaflet; layer config in `lib/map-layers.ts`) and `app/sites/[id]/page.tsx` (hour slider, report and rating forms). Allen Coral Atlas overlays are prebuilt static tiles in `public/overlays/`.
- **Time**: forecast/report times are Maldives wall-clock strings (UTC+5); use `toMaldivesWall` / `parseWall` from `forecast.ts` rather than raw `Date` parsing.

## Tests layout

Unit tests sit next to modules in `lib/`; `tests/` holds the API route tests (`api-v1*.test.ts`, with `fake-d1.ts`), `hour-slider.test.ts` and `replay-cli.test.ts` (the `npm run replay` runner, in process). A test must not write into `data/` (use a temp dir) and should catch a bug no other test catches: the 4-tier requirements suite and the milestone challenger tests were removed in Nov 2026 because they added no coverage the unit tests lacked. `data/benchmark-reports.json` holds curated fixture scenarios, not real ground truth: the replay skips lagoon sites and reads walls along the reef, so it scores 30 of its reports. Tests that need the head term or the lagoon model build ring levels or sources themselves (no network).

## Deployment

`output: "standalone"`; `Dockerfile` + `docker-compose.yml` bind-mount `./data` for persistence, so the host's `data/` (catalog, rims, store, marine cache) is what the running app reads.

The same code also runs on Cloudflare Workers (`CLOUDFLARE.md`): read-only data files ship as static assets, the store lives in D1 and the marine cache in R2, picked at run time by `lib/cloudflare.ts`. PR branches deploy with `wrangler preview`, which reads only the `previews` block of `wrangler.jsonc` (its own D1 database and R2 bucket); a new binding needs a preview copy there (except `CACHE`: without it previews keep their caches in `DATA`). Every server action must `await ready()` before reading data, and state holding in-flight promises must go through `perRequest` (`inFlightPerRequest` for a map of promises by key); a new data file the app reads goes in `DATA_FILES` (`lib/data-files.ts`; a large file only one feature needs goes in `ON_DEMAND_DATA_FILES` too, and its actions call `readyWith("<file>")` (`lib/ready.ts`)) and is read with `readDataFile` (or `readDataFileIfPresent` when a missing file means none).
